# Отчёт тимлида: фундамент CZUZE и структура проекта

Дата: 15 ноября 2026 года.

Рабочий репозиторий команды: [Lordtop4ik/szuze_website_security](https://github.com/Lordtop4ik/szuze_website_security).
Исходный магазин перенесён из [Czuze](https://github.com/itmo-workshop-09-11-2026/Czuze), коммит `f1c84a2`. Перенос выполнен поверх начального коммита целевого репозитория, без перезаписи его истории.

## 1. Что уже сделано

- Сервер магазина переведён с `http.server` на **FastAPI + Uvicorn**. Существующие расчёты заказов, промокод, остатки и административный API сохранены.
- Добавлены **регистрация, вход и выход**. Пароли хранятся как хеши Argon2, пользователи и сессии — в SQLite. Сессия действует 24 часа; выход отзывает её на сервере.
- Каталог открыт гостям. Для подтверждения заказа нужен вход; после входа пользователь возвращается к оформлению, корзина сохраняется.
- Добавлена проверка **CSRF-токена** для отправки форм и создания заказа. Это защита от поддельных запросов от имени пользователя; она не заменяет антибот-механизмы задания.
- Новые заказы связаны с пользователем. Повтор запроса по `requestId` учитывает владельца. Существующая база обновляется без удаления товаров и заказов.
- Ссылка входа, формы и кнопка выхода оформлены в стиле магазина: общие цвета, шрифты, поля и кнопки.
- Настроены **pytest, автозапуск сервера для тестов и GitHub Actions** на Linux и Windows. Обновлены README, команды Makefile и Dockerfile.
- Локальные базы, окружение, секреты, кэши и рабочие заметки исключены из Git. Автопубликация GitHub Pages отключена: авторизация работает через Python-сервер.

## 2. Где что находится

### Как проходит запрос

```text
Браузер → Uvicorn → FastAPI в webapp.py
                       ├─ /login, /register → templates/auth.html
                       ├─ /api/... → обработчик → ShopService → SQLite
                       └─ / и ресурсы → site/
```

`create_app()` собирает приложение, а его `lifespan` подготавливает базу при запуске. Маршруты API и форм объявлены **до** `app.mount('/')`: монтирование статики должно оставаться последним, иначе оно может перехватить запросы к новым маршрутам.

### Что хранится на сервере, а что в браузере

В SQLite есть таблицы `products`, `orders`, `users`, `sessions`. Пароли в открытом виде не записываются. В cookie находится случайный токен сессии, а в базе — его хеш; cookie имеет HttpOnly и SameSite=Lax.

Корзина и избранное сохраняются в браузере. История заказов в интерфейсе тоже локальная, разделена по ID пользователей и не синхронизируется между устройствами. При этом сами заказы и их владельцы записываются в серверную БД. Старые анонимные заказы не назначаются новым аккаунтам.

## 3. Как начать работу

Самый простой запуск: установить и запустить Docker Desktop (на Linux — Docker Engine с Compose v2), клонировать репозиторий и выполнить в его корне `docker compose up --build`. Сайт откроется на http://localhost:8000. Остановка — `docker compose down`, база сохраняется в именованном томе. Python и Node.js на компьютере для этого не нужны. При занятом порте можно задать `HOST_PORT=8001` в необязательном `.env`; подробности — в README.

Для разработки и запуска тестов без Docker:

Нужны Git, Python 3.12+ и Node.js 22+ для JavaScript-проверок. Запускать команды нужно из корня репозитория.

```sh
git clone https://github.com/Lordtop4ik/szuze_website_security.git
cd szuze_website_security
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python main.py
```

В Windows создание окружения: `py -3.12 -m venv .venv`. Активация в PowerShell: `.venv\Scripts\Activate.ps1`, в cmd: `.venv\Scripts\activate.bat`. Последующие команды с `python` одинаковы.

Сайт: **http://localhost:8000**. Остановка: Ctrl+C. При первом запуске автоматически появится `data/shop.sqlite3` с товарами. Отдельно запускать сервер перед pytest не нужно.

При запуске через Python переменные задаются в оболочке; автоматического чтения `.env` нет. Compose читает необязательный `.env` автоматически:

| Переменная | Значение и назначение |
| --- | --- |
| `HOST` | По умолчанию `127.0.0.1`: доступ с этого компьютера. |
| `PORT` | По умолчанию `8000`. |
| `SHOP_DB` | Путь к SQLite; по умолчанию `data/shop.sqlite3`. База должна находиться вне публичной папки `site/`. |
| `SHOP_ADMIN_TOKEN` | Включает изменение каталога через административный API. Без него изменение отключено. |
| `COOKIE_SECURE` | `0` для локального HTTP; `1` для работы через HTTPS. |

## 4. Маршруты, которые понадобятся команде

| Метод и путь | Что делает |
| --- | --- |
| `GET /` | Открывает магазин. Разделы переключаются query-параметром, например `/?view=cart`. |
| `GET /login`, `GET /register` | Выдаёт HTML-форму и CSRF-токен в скрытом поле. |
| `POST /login`, `POST /register` | Принимает HTML-форму: `username`, `password`, `csrf`, необязательный `next=checkout`. |
| `POST /logout` | Принимает HTML-форму с `csrf`, отзывает сессию. |
| `GET /api/auth/me` | Возвращает текущего пользователя либо `null` и CSRF-токен. Гостю при необходимости создаёт анонимную сессию. |
| `GET /api/products` | Возвращает каталог; необязательные параметры `q` и `category` фильтруют товары. |
| `POST /api/orders` | Создаёт заказ. Требует авторизованную cookie-сессию и заголовок `X-CSRF-Token`. |
| `PUT /api/products/{id}` | Обновляет или создаёт товар по `X-Admin-Token`. Пользовательский вход не даёт административного доступа. |

Формы отправляются как `application/x-www-form-urlencoded`, API заказов — как `application/json`. Тело заказа: `{"items":[{"productId":"duck","quantity":1}],"requestId":"example-1"}`; дополнительно можно передать `promo: "DEBUG10"`.

Успешные вход и регистрация возвращают redirect `303`. Ошибки авторизации: `401` — неверные учётные данные; `403` — неверный CSRF; `409` — занятый логин; `422` — неверный формат полей. Логин: 3–32 латинских буквы, цифры или `_`, регистр не учитывается. Пароль: 8–128 символов.

Ошибки API представлены как `{"error":"сообщение"}`. `POST /api/orders` без входа возвращает `401`, поэтому бот-симулятор для проверки оформления должен сначала получить CSRF и выполнить вход. Для проверки отказа на сетевом уровне вход не нужен.

## 5. Где подключать ваши задачи

### Пара «Сетевой щит»

Ваша часть: фильтрация IP дата-центров, ограничение числа запросов и проверка User-Agent. Подключайте проверки как middleware внутри `create_app()` до выполнения обработчиков страниц и API. Алгоритмы удобно вынести в свой модуль, чтобы не создавать большой конфликт в `webapp.py`.

В `webapp.py` уже есть `client_ip(request)`, возвращающая адрес из `request.client`. Пока это заготовка: будущие сетевые проверки должны явно вызывать её. В тестах её можно подменять через `monkeypatch.setattr(webapp, 'client_ip', ...)`. Запуск через `main.py` отключает доверие к proxy-заголовкам: произвольный `X-Forwarded-For` не считается достоверным адресом.

Добавляйте положительные и отрицательные тесты на разрешённый/заблокированный IP, число запросов и User-Agent. Тесты не должны зависеть от реального внешнего IP или ждать настоящую минуту: источник времени для лимитера следует сделать подменяемым.

### Пара «Ловушки для ИИ и Формы»

Ваша часть: CSS-honeypot, учебная ложная инструкция в HTML и выбранная бонусная задача. Разметку добавляйте в `templates/auth.html`, CSS — в `site/styles.css`. Серверная точка подключения — `authenticate()` в `webapp.py`: после чтения формы и проверки CSRF, до создания пользователя или проверки пароля.

Один шаблон обслуживает вход и регистрацию, поэтому проверяйте обе формы. Существующие поля `username`, `password`, `csrf` и `next` нужно сохранить. Ложная инструкция — содержимое страницы для эксперимента с ботами; её не нужно исполнять на сервере.

Добавляйте тесты на обычное заполнение и на срабатывание ловушки. Для бонуса по времени подменяйте часы; для симулятора достаточно `httpx` или `requests`. При тестировании ловушек отправляйте действующий CSRF, иначе запрос будет отклонён раньше вашей проверки.

### Как объединяем изменения

Каждая пара создаёт отдельную ветку, прикладывает свои тесты и открывает PR в `main`. До параллельных правок согласуйте места изменения `webapp.py`, поскольку обе пары будут подключать туда свой код. Тимлид проверяет PR и результаты CI, затем объединяет изменения.

**Сейчас ни одна из пяти антибот-защит и бонусная задача не реализованы.** Фундамент и обычная авторизация готовы для их подключения. Эффективность блокировки ботов и отсутствие ложных срабатываний предстоит проверять отдельно на согласованных сценариях.

## 6. Проверки и текущий результат

```sh
python -m pytest -q
node tests/shop.test.cjs
python tests/smoke.py
# Или всё вместе при активированном окружении и наличии make:
make test
```

| Файл | Что проверяет |
| --- | --- |
| `tests/conftest.py` | Сессионная фикстура `live_server`: временная БД, запуск Uvicorn на свободном порту, ожидание готовности и остановка процесса после тестов. |
| `tests/test_auth.py` | Доступность страниц через настоящий сервер; регистрация, вход, выход, CSRF, истечение сессии, владелец заказа и обновление старой базы. |
| `tests/test_api.py` | Каталог, административный токен, валидация, остатки, откат неуспешного заказа, конкурентное списание, повтор заказа и сохранение данных. |
| `tests/test_pack.py` | Сохранность предыдущего ZIP при ошибке чтения файлов. |
| `tests/shop.test.cjs` | Правила корзины, поиск, скидки, сохранённые данные и корректность 3D-моделей. |
| `tests/smoke.py` | Упаковка ZIP, запуск сервера, ресурсы, MIME-типы и недоступность серверных файлов через HTTP. |

После реализации полный локальный `make test` прошёл. После исправления оформления повторно прошли 5 pytest-тестов; главная, вход и регистрация проверены в браузере. [CI последнего изменения кода](https://github.com/Lordtop4ik/szuze_website_security/actions/runs/43741140928) завершился успешно на Linux и Windows с Python 3.12. Локально pytest выдаёт предупреждение об устаревшем API зависимости Starlette/AnyIO, без падения тестов.

Для демонстрации: открыть магазин гостем → добавить товар → перейти к подтверждению → зарегистрироваться → подтвердить заказ → проверить историю → выйти. Затем показать автоматические тесты.

## 7. Что пока не входит в результат

Публичный хостинг, восстановление пароля, подтверждение почты и синхронизация истории между устройствами не делались. `python main.py --pack` создаёт только статическую демоверсию магазина, без серверного входа. Для Docker Compose добавлена отдельная проверка в CI: сборка, запуск и сохранение данных после пересоздания контейнера. Локально Docker не установлен, поэтому контейнерные проверки выполняются в GitHub Actions. Том Compose и база обычного Python-запуска независимы.
